01 · Scan layer

Deterministic by construction

Every tool is pinned — Python tools by version, docker tools by immutable digest — so a scan on your laptop is byte-for-byte the scan in CI. A missing toolchain skips its dimension, never blocks you. Runs zero-config; tune one committed .security-audit.conf per project.

02 · Judgment layer

Scanners emit findings. They don't decide.

Five Claude Code skills add the judgment a script can't: real-vs-false-positive triage with a confidence gate, and semantic passes for the flaw classes no rule engine can express. Deep passes are trigger-based, not per-push — they run when the code changes in a way that warrants them.

/sec-auditone command

The orchestrator: runs the scan, triages, then only the deep passes that actually apply to the repo — signal-gated, and it says why before spending tokens.

/sec-triageroutine

After every scan with findings: exclusions → reachability → confidence ≥ 0.7, with a CISA KEV / EPSS check. FP → allowlist, REAL → fix or follow-up registry.

/sec-sast-deeptrigger

Semantic flaws semgrep's patterns can't see: horizontal authz / IDOR, missing-role checks, business logic, second-order injection — by following the call path.

/sec-ai-reviewtrigger

OWASP LLM Top 10 for code that calls an LLM: prompt injection, insecure output handling, excessive agency, system-prompt disclosure, model supply chain.

/sec-threat-modeltrigger

STRIDE + data-flow mapping of the attack surface: what could go wrong by design, and what isn't defended — a living threat-model document.

—DAST / autonomous pentesting

Executes attacks against a running target — explicitly rejected. The planned PoC mode is generate-only: it writes a proof-of-concept for a human to review, never runs it.

—CSPM

Requires cloud credentials and an inventory service; a repo-vendored kit has neither. Use a dedicated tool (e.g. Prowler) alongside the kit.

—Runtime protection

An agent living inside your production process is a different product category. The kit stops at the repo boundary.

—Compliance dashboards

A SaaS surface. The kit emits SARIF and summary.json; whatever consumes them can build the dashboard.

04 · Trust

The kit audits itself

A security tool must survive its own standards. The kit dogfoods its secret + sast scans on its own repo in CI, and every install path is designed to be reviewed before it runs.

▚No curl | bash

The documented install is download → read → run. Piping a remote script into a shell is the exact anti-pattern the kit warns against.

▚Pinned everything

Python tools by version, docker tools by immutable digest, the kit itself by tag + resolved SHA in a committed .kit-version — no drift vs CI.

▚Tag-repoint guard

If a pinned ref suddenly resolves to a different commit, bootstrap refuses. Enforce further with --expect=<sha>.

▚CHECKSUMS manifest

scan.sh verify checks every kit file against a committed sha256 manifest and flags rogue extra files under skills/.

▚Hard boundary

Internal evidence only — the kit does not replace PCI DSS 11.3.2 ASV scans or 11.4 pentests. It catches what leaked into code, early.

▚MIT & forkable

Public, MIT-licensed, skills are readable AI instructions. The only official repo is boraeresici/security-audit-kit; review before running.

05 · Why

The checks we run on our own work — released for everyone

security-audit-kit didn't start as a product. It's the gate we run on our own development.

During development, the same questions come up at the same steps: did a secret leak into the git history? Did a dependency pick up a known CVE? Is the infrastructure configuration safe? We wanted those answers locally and deterministically — so we started running these checks ourselves, before CI/CD ever sees the code.

We believe a tool this fundamental should belong to everyone. So the kit is distributed as free, open-source software under the MIT license: add it to your repo, read every line before you run it, fork it, adapt the skills to your own team. No accounts, no telemetry, no paywall between you and your own security evidence.

It carries the same discipline it asks of you — pinned versions, checksummed files, an install that tells you to read it first. If it makes one more project scan before it ships, it has done its job.

And it keeps maturing — with your contributions.
